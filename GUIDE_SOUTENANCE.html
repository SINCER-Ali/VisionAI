PARTIE 1 — Vue d'ensemble & architecture

Le pitch (à réciter)

VisionAI est un moteur de Machine Learning codé from scratch en Rust, sans bibliothèque ML. Le cœur mathématique (vecteurs, matrices, fonctions d'activation) est dans la crate core_lib, sur laquelle on a construit 4 modèles : linéaire, MLP (perceptron multi-couches), RBF (réseau à fonctions de base radiale) et SVM (machine à vecteurs de support). On expose ce moteur de deux façons : un binding Python via PyO3 (pour entraîner et expérimenter dans des notebooks), et une API REST en Axum qui sert les prédictions à un client web. La donnée : des images redimensionnées en 64×64×3 = 12288 valeurs, classées en 3 catégories : aucun, humain, animal.

Schéma du flux

   Images 64×64×3 (12288 valeurs normalisées entre 0 et 1)
        │  preprocess_dataset.py  (Python + PIL)
        ▼
   datasets/X_train.npy, y_train.npy ...
        │  train_and_save.py  → appelle vision_ai.PyMLP (le binding Rust)
        ▼
   models/mlp_weights.json   (les poids entraînés)
        │  lu au démarrage par le serveur
        ▼
   api_server (Axum, port 3000) :  /predict  /models  /train  /reload-models  /health
        │  requêtes HTTP (fetch)
        ▼
   client/index.html  (upload image → POST /predict → affiche classe + confiance)

Le workspace (organisation des crates)

C'est un workspace Rust = plusieurs sous-projets (« crates ») dans un seul dépôt :

Crate Rôle
core_lib la bibliothèque : maths + modèles + optimisation. Ne fait rien toute seule.
python_binding enrobe core_lib pour l'appeler depuis Python (module vision_ai).
api_server un binaire : le serveur web qui utilise core_lib.
client le front web (HTML/CSS/JS pur, aucune dépendance).

Q : Pourquoi séparer en plusieurs crates ? R : Séparation des responsabilités. core_lib est réutilisable et testable indépendamment ; le serveur et le binding ne font que l'utiliser. Si on change le serveur, le moteur ML n'est pas touché.

PARTIE 2 — Justifier RUST (la question qui fait peur)

« Pourquoi Rust alors que vous n'avez pas eu de cours ? »

4 arguments (3 techniques + 1 honnête) :

  1. Performance : Rust compile en code natif (comme C/C++), sans interpréteur ni ramasse-miettes (garbage collector). Pour du ML from scratch où on fait des millions de multiplications de f64, c'est rapide.
  2. Sécurité mémoire à la compilation : le système d'ownership (propriété) et le borrow checker (vérificateur d'emprunts) garantissent qu'il n'y a ni fuite mémoire, ni accès invalide, ni data race, et tout ça sans GC. C'est l'argument phare de Rust.
  3. Typage fort + pas de null : les erreurs sont attrapées par le compilateur (via Option et Result), pas en plein entraînement.
  4. Honnête : « On l'a aussi choisi comme défi d'apprentissage, pour sortir de Python. » Le jury respecte l'honnêteté.

Les concepts Rust à savoir expliquer (en 1 phrase chacun)

Concept Explication simple Où dans ton code

« Vec ou HashMap ? » (ta peur précise)

  • Vec<f64> → données numériques indexées par position (0, 1, 2…), stockées de façon contiguë → rapide pour le calcul. On itère, on indexe par numéro.
  • HashMap<String, ...> → on retrouve un élément par une clé (ici le nom du modèle). On cherche par nom.

Règle à réciter : indexé par un numéro de position → Vec ; indexé par une clé/nom → HashMap.

Les « pointeurs » en Rust

Rust n'utilise quasiment jamais de pointeurs bruts. Ce que tu as : - &T = référence partagée (lecture). &mut T = référence unique (écriture). - Arc<T> = Atomic Reference Counted : permet de partager le même objet entre plusieurs threads (compteur de références). - RwLock<T> = Read-Write Lock : plusieurs lecteurs OU un seul écrivain à la fois. - Dans le serveur : Arc<RwLock<HashMap<...>>> = un état partagé entre toutes les requêtes, protégé contre les accès concurrents. C'est pour ça que /predict fait .read() et /train fait .write().

📄 core_lib/src/math/vector.rs — la brique de base

struct Vector { len: usize, data: Vec<f64> } : un vecteur mathématique.

Méthodes clés : - dot(&self, other) → produit scalaire : Σ aᵢ·bᵢ. Implémenté avec .iter().zip().map().sum(). - add / sub → addition/soustraction terme à terme. - hadamard → produit élément par élément (≠ produit scalaire) : [a₁b₁, a₂b₂, …]. Sert dans la backpropagation. - scale(alpha) → multiplie tout par un scalaire. - l2_norm → √(v·v) = longueur du vecteur. - argmax → l'indice de la valeur max → sert à choisir la classe prédite.

Questions probables :

Q : Pourquoi stocker len alors que data.len() existe déjà ? R : C'est redondant. On pourrait supprimer len et faire une méthode fn len(&self) -> usize { self.data.len() }. → bonne réponse « amélioration possible ».

Q : Que fait zip dans dot ? R : zip associe deux itérateurs par paires : [a₁,a₂] et [b₁,b₂] → [(a₁,b₁),(a₂,b₂)]. Ensuite map(\|(a,b)\| a*b) multiplie chaque paire, et sum() additionne.

Q : À quoi sert assert_eq!(self.len, other.len) ? R : Vérifie que les deux vecteurs ont la même taille avant le calcul. Sinon le programme panique avec un message clair plutôt que de produire un résultat faux.

Q : Comment remplacer la boucle de argmax ? R : Par un itérateur : self.data.iter().enumerate().max_by(\|a,b\| a.1.partial_cmp(b.1).unwrap()).map(\|(i,_)\| i). (On utilise partial_cmp car les f64 ne sont pas totalement ordonnés à cause de NaN.)

📄 core_lib/src/math/matrix.rs

struct Matrix { rows, cols, data: Vec<f64> } : matrice stockée à plat (row-major), c.-à-d. l'élément (i,j) est à l'indice i * cols + j.

Méthodes : - multiply → produit matriciel classique (triple boucle i,j,k). assert_eq!(self.cols, other.rows) car pour multiplier A(n×m)·B(m×p), il faut m = m. - transpose → échange lignes/colonnes : result[j][i] = self[i][j]. - from_flat → construit une matrice depuis un Vec plat (avec vérification de taille).

Q : Pourquoi stocker la matrice à plat (1D) plutôt qu'en Vec<Vec<f64>> ? R : Mémoire contiguë = plus rapide (cache CPU) et plus simple à sérialiser. On calcule l'indice nous-mêmes avec i*cols + j.

Q : Complexité de multiply ? R : O(n·m·p) à cause des 3 boucles imbriquées.

📄 core_lib/src/math/activations.rs

Les fonctions d'activation (introduisent la non-linéarité) et leurs dérivées (pour la backprop) :

Fonction Formule Usage
sigmoid 1/(1+e⁻ˣ) sortie entre 0 et 1
tanh tanh(x) sortie entre -1 et 1
relu max(0, x) couches cachées (rapide, évite le vanishing gradient)
softmax eˣⁱ / Σeˣʲ couche de sortie en classification : transforme des scores en probabilités qui somment à 1

L'enum Activation + match permet de choisir l'activation dynamiquement (apply / derivative).

Q : Pourquoi softmax soustrait le max (x - max) ? R : Stabilité numérique. e^(grand nombre) déborde (overflow → inf). Soustraire le max garde les exposants ≤ 0, donc e^… ≤ 1. Le résultat mathématique est identique.

Q : Pourquoi la dérivée de softmax renvoie [1.0, 1.0, …] ? R : Parce qu'avec une perte cross-entropy, la dérivée combinée softmax+perte se simplifie en sortie − cible. On calcule donc directement ce delta dans train, et la « dérivée » de softmax est neutralisée (multipliée par 1).

Q : Pourquoi ReLU dans les couches cachées et softmax en sortie ? R : ReLU est simple et efficace pour apprendre des représentations ; softmax donne des probabilités interprétables pour les 3 classes.

📄 core_lib/src/models/mod.rs

pub type Vector = Vec<f64>;          // ⚠️ alias (voir piège n°1)
pub struct TrainConfig { learning_rate: f64, epochs: usize }
pub trait Model {
    fn predict(&self, input: &Vector) -> Vector;
    fn train(&mut self, inputs: &[Vector], targets: &[Vector], config: &TrainConfig);
}

Le trait Model = le contrat commun : tout modèle doit savoir predict et train. LinearModel l'implémente.

Q : Pourquoi un trait ? R : Pour uniformiser l'interface des modèles : on peut écrire du code générique qui marche pour n'importe quel Model. C'est le polymorphisme en Rust.

Q : Différence &[Vector] vs Vec<Vector> ? R : &[Vector] est une slice (vue empruntée sur un tableau) — on ne prend pas possession des données, on les lit. Plus flexible et moins coûteux.

📄 core_lib/src/models/linear.rs — le modèle linéaire

struct LinearModel { weights: Vec<f64>, bias: f64, input_size }

predict : ŷ = bias + Σ wᵢ·xᵢ (une seule sortie, c'est une régression linéaire).

train : descente de gradient minimisant l'erreur quadratique (ŷ − y)² :

error = prédiction − cible
wᵢ  -= lr · 2 · error · xᵢ      // dérivée de (ŷ-y)² par rapport à wᵢ
bias -= lr · 2 · error

Q : D'où vient le 2 dans la mise à jour ? R : C'est la dérivée de la perte (ŷ−y)² : d/dw (ŷ−y)² = 2·(ŷ−y)·x. Le 2 pourrait être absorbé dans le learning_rate.

Q : Le modèle linéaire fait une seule sortie, comment classifier en 3 classes ? R : Dans le serveur, on utilise une stratégie One-vs-Rest : 3 modèles linéaires (un par classe), et on prend la classe au score le plus élevé (argmax), normalisé par softmax. (Voir main.rs.)

📄 core_lib/src/models/mlp.rs — le perceptron multi-couches ⭐

C'est le cœur que le jury va creuser. Structure : - Layer { weights: Vec<Vector>, biases: Vector, input_size, output_size } : une couche = une matrice de poids (un Vector par neurone) + des biais. - MLP { layers: Vec<Layer>, hidden_activation }.

MLP::new(&[12288, 64, 3]) :

layer_sizes.windows(2).map(|w| Layer::new(w[0], w[1]))

windows(2) glisse une fenêtre de 2 : [12288,64] puis [64,3] → 2 couches (une cachée de 64 neurones, une de sortie de 3).

forward (une couche) : sortie = biais + W·entrée (chaque neurone fait weights[i].dot(input)).

predict : passe dans chaque couche ; ReLU sur les cachées, softmax sur la dernière.

train (backpropagation) — la séquence à comprendre : 1. Forward : on stocke les z (pré-activations) et les activations de chaque couche. 2. Delta de sortie : delta = sortie − cible (gradient softmax + cross-entropy). 3. Rétropropagation (de la dernière couche vers la première) : - Mise à jour : weights[i][j] -= lr · delta[i] · a_prev[j] et biases[i] -= lr · delta[i]. - Propagation du delta : new_delta[j] = Σᵢ weights[i][j]·delta[i], puis delta = new_delta ⊙ relu'(z) (⊙ = hadamard).

Q : Qu'est-ce que la backpropagation ? R : L'algo qui calcule comment chaque poids contribue à l'erreur, en propageant le gradient de la sortie vers l'entrée via la règle de la chaîne (dérivées composées), puis ajuste les poids dans le sens qui réduit l'erreur.

Q : Pourquoi delta = sortie − cible directement, sans dériver softmax ? R : Parce que softmax + cross-entropy se simplifient en sortie − cible (voir activations).

Q : Que fait .rev() dans la boucle ? R : On parcourt les couches de la dernière à la première, car la backprop remonte le réseau.

Q : Rôle de hadamard ici ? R : Multiplier le delta propagé par la dérivée de ReLU terme à terme (la dérivée est 1 si z>0, sinon 0).

Q : #[serde(default = "default_activation")] sur hidden_activation ? R : Si on charge un vieux JSON qui n'a pas ce champ, serde met ReLU par défaut → compatibilité ascendante.

📄 core_lib/src/models/rbf.rs — réseau à fonctions de base radiale (RBF)

⚠️ Important : c'est la version struct RBF (celle du dépôt final). Elle utilise le paramètre gamma (γ) et entraîne ses poids par moindres carrés, pas seulement par descente de gradient.

Principe : au lieu de couches linéaires, on a des centres ; chaque neurone caché mesure la proximité de l'entrée à un centre via une gaussienne.

  • rbf_kernel(x, c, γ) = exp(−γ·‖x−c‖²) → vaut 1 si x = centre, décroît avec la distance.
  • compute_activations : le vecteur des φ(x, cᵢ) pour chaque centre.
  • predict_raw : sortie = W·φ + biais. predict : softmax(predict_raw).
  • Entraînement (3 étapes) : 1. init_centers_random — choisit n_centers exemples au hasard comme centres (mélange de Fisher-Yates). 2. solve_weights — calcule les poids analytiquement par moindres carrés régularisés : W = (ΦᵀΦ + λI)⁻¹ ΦᵀY, résolu par élimination de Gauss-Jordan avec pivot partiel. 3. Raffinement optionnel par descente de gradient (cfg.epochs étapes).

Q : Différence MLP vs RBF ? R : Le MLP apprend par rétropropagation sur toutes les couches. Le RBF a une couche cachée fixe (centres + gaussiennes) et calcule la couche de sortie directement par moindres carrés → entraînement très rapide.

Q : Rôle de gamma (γ) ? R : Contrôle la largeur des gaussiennes. γ grand → influence très locale (risque de sur-apprentissage) ; γ petit → tout se ressemble (sous-apprentissage). (Lien avec sigma : γ = 1/(2σ²).)

Q : Rôle de lambda (λ) ? R : Régularisation ridge : le +λI évite que la matrice ΦᵀΦ soit non-inversible et stabilise la solution (évite le sur-apprentissage).

Q : Qu'est-ce que l'élimination de Gauss-Jordan ? R : Une méthode d'algèbre linéaire pour résoudre un système (ici inverser une matrice) en transformant la matrice augmentée en forme réduite, avec pivot partiel (on choisit le plus grand pivot) pour la stabilité numérique.

📄 core_lib/src/models/svm.rs — machine à vecteurs de support (SVM)

Idée : un SVM cherche l'hyperplan qui sépare les classes avec la plus grande marge (la plus grande « rue » vide entre les classes).

  • enum KernelType : Linear (a·b), RBF { gamma } (exp(−γ‖a−b‖²)), Polynomial { degree, coef0 } ((a·b + coef0)^degree).
  • struct SVM : multi-classes en one-vs-rest (un classifieur binaire par classe), via BinaryLinearSVM ou BinaryKernelSVM.
  • new_linear(c) / new_kernel(c, kernel) : c = paramètre de régularisation (compromis marge / erreurs).
  • predict : softmax des scores OvR, argmax = classe.
  • train : SVM linéaire → hinge loss + SGD (style Pegasos) ; SVM à noyau → SMO.

Q : C'est quoi la « marge » ? R : La distance entre l'hyperplan séparateur et les points les plus proches de chaque classe (les vecteurs de support). Le SVM la maximise pour mieux généraliser.

Q : C'est quoi la hinge loss ? R : La perte max(0, 1 − y·(w·x + b)) : nulle si le point est bien classé avec une marge ≥ 1, sinon elle pénalise proportionnellement. C'est ce qui pousse à la grande marge.

Q : À quoi sert le « noyau » (kernel trick) ? R : À séparer des données non linéairement séparables sans calculer explicitement les coordonnées dans un espace de plus grande dimension : on remplace le produit scalaire par une fonction noyau (RBF, polynomial).

Q : Rôle du paramètre C ? R : Le compromis entre grande marge (C petit) et peu d'erreurs d'entraînement (C grand). Trop grand → sur-apprentissage.

📄 core_lib/src/optim/ — les optimiseurs

Un optimiseur = la stratégie pour ajuster les poids à partir du gradient. 🖼️ Image de la bille qui descend une vallée pour trouver l'erreur minimale.

  • gradient_descent.rs — descente simple : wᵢ -= lr · 2 · error · xᵢ. Pas fixe. La bille avance d'un pas constant. (C'est ce qu'utilise le MLP.)
  • optimizer.rs — le trait Optimizer (update + reset) : interface commune pour rendre les optimiseurs interchangeables.
  • sgd_momentum.rs — descente avec inertie : vitesse = momentum·vitesse − lr·grad ; poids += vitesse. La bille accumule de l'élan → plus rapide, traverse les petits creux. Option Nesterov = anticipe où l'élan mène avant de calculer le pas.
  • adam.rs — le plus malin : garde une moyenne des gradients (m, la direction) et de leurs carrés (v, l'amplitude) → pas adaptatif par poids. β1=0.9, β2=0.999, ε=1e-8.

Q : Learning rate / epoch ? R : Le learning rate est le pas d'apprentissage (trop grand → diverge ; trop petit → lent). Une epoch est un passage complet sur les données.

Q : Différence descente simple vs Adam ? R : La descente simple a un pas fixe identique pour tous les poids ; Adam adapte le pas par poids via deux moyennes mobiles → converge plus vite et plus stablement.

⚠️ Honnêteté : Adam et SGD momentum sont implémentés et testés, mais le MLP utilise encore la descente de gradient simple. Les brancher est une amélioration prévue.

📄 core_lib/src/metrics/mod.rs — les métriques d'évaluation

Mesurent la qualité d'un modèle. Deux familles :

Classification : accuracy (% correct), confusion_matrix (ligne = vrai, colonne = prédit), precision (TP/(TP+FP)), recall (TP/(TP+FN)), f1_score (2·P·R/(P+R), moyenne harmonique), f1_macro (moyenne des F1 par classe).

Régression : mse (erreur quadratique moyenne), mae (erreur absolue moyenne), r_squared (R² : 1 = parfait, 0 = niveau « moyenne »).

Validation : kfold_indices(n, k) → découpe en k parties pour la validation croisée.

Q : Pourquoi le F1 plutôt que l'accuracy ? R : Avec des classes déséquilibrées (humain 287 / animal 407), l'accuracy favorise la classe majoritaire ; le F1 (et le F1-macro) équilibrent précision et rappel par classe.

📄 core_lib/tests/integration_tests.rs — les 72 tests d'intégration

Test unitaire (dans chaque fichier, #[cfg(test)]) = teste une fonction isolée. Test d'intégration (dossier tests/) = teste la bibliothèque de l'extérieur, en combinant les modules (ex. entraîner un MLP complet sur XOR).

Couvre : Vector, Matrix, activations, Linear, MLP (XOR/AND/OR/multiclasse/régression), RBF, SVM (linéaire + noyau), optimiseurs (Adam, SGD momentum), métriques, et des comparaisons de modèles.

Q : Comment lancer les tests ? Pourquoi XOR ? R : cargo test. AND/OR sont linéairement séparables (le linéaire suffit), XOR ne l'est pas → il prouve que les modèles non-linéaires (MLP, RBF, SVM à noyau) fonctionnent vraiment.

📄 python_binding/src/lib.rs — le pont Rust ↔ Python (PyO3)

PyO3 permet d'appeler du Rust depuis Python. Le module exposé s'appelle vision_ai.

Les attributs (macros) : - #[pyclass] → expose une struct Rust comme classe Python. - #[pymethods] → bloc des méthodes appelables depuis Python. - #[new] → le constructeur Python (__init__). - #[staticmethod] → méthode statique (PyMLP.load_json(...)). - #[pyfunction] → fonction Python libre. - #[pymodule] → définit le module et y enregistre classes/fonctions. - #[pyo3(signature = (...))] → définit les paramètres par défaut (ex. n_centers=10).

Classes exposées : PyVector, PyMatrix, LinearRegression, PyMLP, PyRBF, PySVM.

Gestion d'erreurs : les Result Rust sont convertis en exceptions Python (PyValueError, PyIOError…), ex. .map_err(|e| PyIOError::new_err(e.to_string())).

Q : Comment on construit ce module ? R : Avec maturin : maturin build --release compile une wheel Python qu'on installe avec pip. (Sur Colab, c'est ce que font les notebooks.)

Q : Que fait .into_iter().map(CoreVector::from_vec).collect() ? R : Convertit les Vec<Vec<f64>> reçus de Python en Vec<Vector> (la struct Rust), pour les passer au modèle.

📄 api_server/src/main.rs — l'API REST (Axum)

État partagé :

struct AppState {
    models: Arc<RwLock<HashMap<String, StoredModel>>>,  // modèles linéaires (disque)
    models_dir: PathBuf,
    mlp: Arc<RwLock<Option<MLP>>>,                        // le MLP en mémoire
    rbf: Arc<RwLock<Option<RBF>>>,                        // le RBF en mémoire
    svm: Arc<RwLock<Option<SVM>>>,                        // le SVM en mémoire
}

Les modèles MLP / RBF / SVM sont chargés au démarrage depuis models/mlp_weights.json, models/rbf_weights.json, models/svm_weights.json. La prédiction choisit le bon modèle selon model_name ("mlp", "rbf", "svm").

Routes : | Méthode | Route | Rôle | |---|---|---| | POST | /predict | reçoit une image (base64), renvoie classe + confiance | | POST | /train | entraîne un linéaire (⚠️ données synthétiques, voir plus bas) | | GET | /models | liste les modèles chargés (remplit le menu du client) | | POST | /reload-models | recharge les modèles du dossier models/ | | GET | /health | renvoie ok (vérifier que le serveur tourne) |

image_to_vector : décode l'image → redimensionne en 64×64 → RGB → divise par 255 → renvoie un Vector de 12288 valeurs (= 64·64·3).

StoredModel : un enum avec #[serde(tag = "kind")] pour les modèles linéaires chargés depuis le disque (créés par /train). Le MLP, le RBF et le SVM, eux, sont gérés en mémoire (chargés au démarrage).

⚠️ Q : Le /train de l'API entraîne sur quoi ? R : Sur des données synthétiques (un commentaire le dit : « à remplacer par vraies données »). Le vrai entraînement se fait via le binding Python (train_and_save.py). C'est un point d'honnêteté à assumer : « L'endpoint /train est une démo de l'API ; l'entraînement réel passe par Python. »

Q : C'est quoi le CORS dans cors_middleware ? R : Cross-Origin Resource Sharing. Comme le client (fichier index.html) et le serveur sont sur des origines différentes, le navigateur bloque les requêtes par défaut. Le middleware ajoute les en-têtes Access-Control-Allow-* pour autoriser le client.

Q : Pourquoi async fn et tokio ? R : Le serveur est asynchrone : il gère plusieurs requêtes en même temps sans bloquer, grâce au runtime tokio (#[tokio::main]).

Q : read() vs write() sur le RwLock ? R : /predict ne fait que lire le modèle → .read() (plusieurs en parallèle). /train modifie l'état → .write() (accès exclusif).

HTML/CSS/JS pur (aucune dépendance, aucun framework). Logique JS : 1. Upload : clic ou glisser-déposer → FileReader.readAsDataURL → on extrait le base64 (dataUrl.split(',')[1]). 2. Prédiction : POST /predict avec { model_name, image_base64 } → affiche predicted_class + barre de confiance. 3. Rafraîchir : GET /models → remplit le menu déroulant. Si la liste est vide → « -- aucun modèle chargé -- ».

Q : Pourquoi envoyer l'image en base64 ? R : Pour la transmettre comme texte dans un JSON simple. (Alternative plus efficace : multipart/form-data, mais le base64 est plus simple à coder.)

Q : Que fait serverUrl.value.replace(/\/+$/, '') ? R : Enlève les / en fin d'URL pour éviter les doubles slashes (localhost:3000//predict).

PARTIE 4 — Le pipeline de données

preprocess_dataset.py

Lit les images de datasets/train/{aucun,humain,animal} → redimensionne en 64×64 → aplatit et normalise (/255) → découpe en train/test (train_test_split, 80/20) → sauvegarde en .npy.

train_and_save.py

Charge les .npy → crée vision_ai.PyMLP([12288, 64, 3]) → entraîne (lr=0.001, 10 epochs) → calcule l'accuracy sur le test → sauvegarde models/mlp_weights.json.

Q : Que valent les nombres [12288, 64, 3] ? R : 12288 = entrées (64×64×3 pixels) ; 64 = neurones cachés ; 3 = classes de sortie.

Q : Comment encode-t-on les étiquettes ? R : En one-hot : classe 1 → [0,1,0]. (C'est ce que fait la boucle t[int(label)] = 1.0.)

« Quelle est l'accuracy de votre modèle ? » ~70 % (voir mlp_config.json). Honnête : « C'est un MLP simple sur peu d'images et peu d'epochs ; on pourrait améliorer avec plus de données, plus d'epochs, de la normalisation et de la régularisation. »

« Quelles sont les limites de votre projet ? » Peu de données (≈1000 images), modèle simple (pas de convolutions), entraînement court. Améliorations : CNN, data augmentation, plus d'epochs.

« Pourquoi pas un CNN ? » Un CNN serait meilleur pour des images, mais l'objectif pédagogique était d'implémenter les bases from scratch (linéaire, MLP, RBF, SVM) pour comprendre les maths, pas d'atteindre l'état de l'art.

« Comment testez-vous votre code ? » Des tests unitaires Rust (#[test]) dans chaque fichier : produit scalaire, multiplication de matrices, softmax somme à 1, la loss diminue après entraînement, etc. On lance avec cargo test.

« Qu'est-ce que usize / f64 ? » usize = entier non signé pour les tailles/index (taille dépend de la machine). f64 = nombre à virgule flottante 64 bits (double précision).

PARTIE 8 — Glossaire express

  • From scratch : sans bibliothèque ML existante (on code les maths nous-mêmes).
  • Forward pass : calcul de la prédiction (entrée → sortie).
  • Backpropagation : calcul des gradients (sortie → entrée) pour ajuster les poids.
  • Gradient : la pente de la fonction d'erreur ; on descend dans le sens opposé.
  • Loss (perte) : mesure de l'erreur entre prédiction et cible.
  • One-hot : encodage d'une classe en vecteur [0,…,1,…,0].
  • Softmax : transforme des scores en probabilités (somme = 1).
  • Epoch : un passage complet sur les données.
  • Learning rate : taille du pas d'apprentissage.
  • Ownership / Borrow checker : système de Rust qui garantit la sécurité mémoire à la compilation.
  • Crate : un paquet/bibliothèque Rust. Workspace : plusieurs crates ensemble.
